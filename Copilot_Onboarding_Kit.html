First week, day by day

Leo's first week at Northwind. Each day ends with something working, not just something read.

  • Day 1 · Sign in to Copilot in VS Code from the status bar (Setup).
  • Day 1 · Install the Copilot CLI, run copilot version, then /login.
  • Day 1 · Read the Introduction: what Copilot sends to a model and how AI Credits are used.
  • Day 2 · Clone ShipTrack. In Ask, get a tour of the repo layout and the test and lint commands.
  • Day 2 · Read .github/copilot-instructions.md and AGENTS.md so you know the rules the agent follows.
  • Day 3 · Fix one small ticket with /plan then Agent, approvals on Manual.
  • Day 3 · Run pytest -q and ruff check . yourself before you commit.
  • Day 4 · Do one task in the CLI inside a git worktree (VS Code vs CLI).
  • Day 4 · Read the Security guide: approvals, trusted folders, what worktrees don't isolate.
  • Day 5 · Open your first PR, run /review on it, and go through the review checklist below.
  • Day 5 · Propose one improvement to the instructions file from something Copilot got wrong this week.
  • Day 5 · Check your week's usage with /usage and talk to Marco about anything surprising.

Review checklist for AI-generated code

Marco's checklist. Use it on every PR that Copilot touched, your own included.

  • I read every changed line, not just the summary.
  • The change does what the ticket asked, and nothing else (no drive-by rewrites).
  • Tests exist for the happy path and at least two error cases, and I saw them run.
  • Tests check behaviour; none were weakened, skipped or deleted to make the run green.
  • Every import and API call exists in the versions we use (no invented functions or packages).
  • New dependencies are justified in the PR and come from a trusted source.
  • Inputs are validated at the boundary; errors are handled, not swallowed.
  • No secrets, tokens or real customer data in code, tests, fixtures or logs.
  • Queries are parameterised; no raw SQL built from strings.
  • Migrations are new revisions with a working downgrade; applied ones are untouched.
  • Linters pass (ruff check .) and CI is green.
  • I can explain this code to a teammate without Copilot.

Team rollout checklist (for leads)

Marco rolls Copilot out to the ShipTrack and Ledgerly teams. Sam owns the security items.

  • Choose the plan (Business or Enterprise) and confirm the AI Credits allowance per seat with the admin (plans).
  • Decide on Copilot Memory: it is off for Business/Enterprise until an owner enables the policy; set repo scope and fact expiry (7–180 days).
  • Configure content exclusion for sensitive paths, and tell the team it is not a security boundary.
  • Agree an approved MCP server list with Sam; ship shared servers in .mcp.json with no secrets.
  • Add .github/copilot-instructions.md and AGENTS.md to each repo, reviewed like code.
  • Add scoped .github/instructions/*.instructions.md files for tests, migrations and legacy apps.
  • Add preToolUse hooks in .github/hooks/ to deny risky commands (for example pushes to main).
  • Set approval defaults: Manual or Assisted in VS Code; forbid --allow-all outside throwaway sandboxes.
  • Keep branch protection: CI green and one human approval on every PR, agent-written or not.
  • Run the Training Programme with each new joiner; pair Leo with Priya for Lab 3.
  • Review usage monthly (each developer can check /usage); cap long CLI runs with --max-ai-credits or /limits set max-ai-credits.
  • Hold a 30-minute retro after four weeks: what to add to instructions, skills and hooks.

Do's and don'ts

DoDon't
Plan first with /plan for anything bigger than a small fix.Ask for a whole feature in one vague prompt.
Name files, constraints and how to check the result.Expect the model to guess your conventions.
Keep approvals on; approve once when unsure.Use --allow-all or /yolo on your main machine.
Use a branch or worktree per agent session.Run two agents in the same folder on the same files.
Run the tests yourself and read the full diff.Merge because the agent said "all tests pass".
Put recurring corrections into instructions or a skill.Correct the same mistake in chat every day.
Keep PRs small and single-purpose.Mix a framework upgrade, a refactor and a feature in one PR.
Treat web pages, MCP results and repo text as untrusted input.Let an agent follow instructions it found in a fetched page or issue.
Keep secrets in env vars or a secrets manager.Paste tokens, passwords or customer data into a prompt.
Start a fresh session (or /compact) when context gets long.Keep one session running for days across unrelated tasks.
