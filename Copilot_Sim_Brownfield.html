Step 1
🏢 Scenario

Old code, real money, thin tests

Ledgerly has issued Northwind's invoices for nine years. Nobody on the current team wrote most of it. Finance wants a CSV export, and Marco wants the worst file in the repo split up before anyone adds to it.

northwind/ledgerly · issue #412requested by Finance · owner: Priya
Export invoices as CSV Finance copies invoice data out of the admin by hand every month-end. Request: GET /reports/invoices.csv?from=YYYY-MM-DD&to=YYYY-MM-DD Columns: number, customer, issued_at, status, net, tax, total, currency Who: staff with permission to view invoices only Also (#398, Marco): invoices/views.py is ~600 lines; split it before adding more views.
FactValue
FrameworkDjango 3.2 (LTS support ended April 2024), upgrade to 4.2 planned
Size~60k lines; apps billing, customers, invoices, payments, reports
Async workCelery tasks for PDF generation, reminders, payment reconciliation
TestsDjango test runner, ~30% line coverage, almost none on invoices/views.py

Risk: silent money bugs

A rounding or tax change can pass every existing test and still be wrong on real invoices.

Risk: confident wrong answers

Copilot has never seen this repo's history. Its explanations must be checked against code.

Risk: big-bang changes

An agent can rewrite 600 lines in one go. Nobody can review that, and the tests would not catch it.

The plan

Understand→Write it down→Pin behaviour→Small feature→Refactor in a worktree→Upgrade notes→Review

🧷 Safety net

Record what the code does today, even if it looks wrong

A characterization test asserts current behaviour, not intended behaviour. It turns "I hope nothing changed" into a failing test when something does. Leo writes them, with Priya pairing.

🤖 VS Code · Copilot Chat Agent · ledgerly
Leo
Write characterization tests in invoices/tests/test_characterization.py for invoices/services.py calculate_totals and for the invoice list and detail views in invoices/views.py. Capture current behaviour exactly, including anything that looks like a bug. Do not change any production code. Add a comment "# CURRENT BEHAVIOUR:" on surprising cases and list them at the end. Then run the invoices tests and coverage for invoices/.
Copilot
Added 21 tests. Surprising behaviour found:
  1. The discount is applied after tax, so tax is charged on the undiscounted amount.
  2. An invoice with zero lines renders a total of None, not 0.00.
  3. The list view shows cancelled invoices to non-staff users.
I did not change any production code.

Do not let the agent "fix" what it finds. The after-tax discount may be a bug, or a contract term with a customer. Log it as an issue, keep the test, and change behaviour only in a separate, deliberate PR.

Instead of git worktree add, the CLI can create one for you: /new worktree starts a new session in a fresh worktree, and /worktree moves work into one. The worktreeBaseRef setting chooses whether it starts from head or the default branch.

In the VS Code Agents window, pick New Worktree in the isolation dropdown instead of Branch. Worktree sessions there always run with the Allow all permission level, so prefer them for well-tested, low-risk tasks like this one.

⚠️

Worktrees isolate files, not your machine. The agent in ../ledgerly-views-refactor can still reach your network, database and credentials. See Security, Sandboxing, Git Worktrees.

📦 Upgrade

Ask for upgrade notes grounded in this repo

Django 3.2 no longer gets security fixes. Before planning the move to 4.2, Marco wants a list of what will break here, not a generic upgrade guide.

docs/upgrade-django-4.2.md (excerpt)reviewed by Marco
## Must change before 4.0 - `url()` → `re_path()` or `path()`: 6 urls.py files - `force_text` → `force_str`, `ugettext*` → `gettext*`: 5 files ## Must change before 4.1 - Remove `default_app_config` from 3 apps (AppConfig is discovered automatically) ## Settings - Set `DEFAULT_AUTO_FIELD` explicitly to avoid new migrations for every model ## Check manually (Copilot could not confirm) - Celery, django-filter, and the PSP SDK: confirm Django 4.2 support in each project's own changelog ## Suggested order 1. ⚠️

Models are trained up to a cut-off date and can be wrong about library versions. Use real signals (deprecation warnings, failing tests) as the source of truth and check claims against the official Django release notes. Never let an agent bump every dependency in one go.

Brownfield review checklist

  • ✓
    Characterization tests are unchanged in refactor PRs. If one changed, behaviour changed.
  • ✓
    Diff stays inside the files the plan named; no drive-by edits.
  • ✓
    No edits to migrations already on main; no new dependencies.
  • ✓
    Callers checked: views, Celery tasks, templates, management commands, signals.
  • ✓
    Coverage did not drop for the touched app.
  • ✓
    Copilot code review comments answered: fixed or explained.
ℹ️

On github.com, you can also request Copilot as a reviewer on each PR. Its findings are a second pair of eyes, not an approval. How it uses repository instructions and auto-review options depend on settings this guide has not verified; check the official code review docs.

🧰 Patterns

Brownfield prompt patterns

The prompts that worked on Ledgerly, generalised. Copy them into your own chats or turn the best ones into a skill.

PatternPrompt shapeUse when
Explain with sources"Explain how X works. Cite a file path for every claim. Say 'not sure' rather than guess."Onboarding, before any change
Trace a path"Show the call path from URL/task Y to Z, one hop per line."Debugging, impact analysis
Pin behaviour"Write characterization tests for X. Capture current behaviour, including bugs. Don't change production code; list surprises."Before refactors and risky edits
Smallest change"What's the smallest change to do Y? List files and why, then stop."Any new feature
Follow the local pattern"Implement Y the same way as @reports/views.py monthly_summary."Keeping style consistent
One refactor step"Step N only: move A to B. No behaviour change, no renames. Run tests, then stop."Large-file refactors
Blast radius"Find every caller of X: views, tasks, templates, signals, management commands."Before changing a signature
Second opinionCLI /rubber-duck on the plan, or /security-review on the diffRisky or security-relevant changes
Grounded researchCLI /research with real warnings and @requirements.txt; ask for linksUpgrades, unfamiliar libraries
💡

The two most useful phrases for legacy code: "then stop" (keeps each turn reviewable) and "no behaviour change" (makes the goal testable). See the Onboarding Kit for a printable prompt cheat-sheet.

🚫 Anti-patterns

How brownfield work with an agent goes wrong

Each of these happened to someone at Northwind at least once.

Anti-patternWhat happensInstead
"Clean up invoices/views.py"A 600-line rewrite nobody can review; subtle behaviour changes ship.Numbered steps, "step N only", tests and a commit after each.
Refactoring before characterization tests30% coverage means most breakage is invisible.Pin behaviour first; check coverage of the file you touch.
Letting the agent fix bugs it discoversA "bug" may be a contract term; Finance numbers change silently.Log an issue, keep the test, change behaviour in its own PR.
Trusting the architecture tourWrong paths and invented modules end up in docs.Open every cited file; mark guesses "(verify)".
"Upgrade everything to latest"Many breaking changes at once; impossible to bisect.Fix deprecations first, then one framework version per PR.
Agent in the main checkout while you workYou and the agent edit the same files.Use a git worktree for longer agent tasks.
Rules only in people's headsEvery new chat repeats the same mistakes.Keep AGENTS.md current; add each repeated correction.
