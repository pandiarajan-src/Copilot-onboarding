🗺️ Map

Six building blocks, each answers one question

Marco wants ShipTrack's standards applied the same way whether Priya works in VS Code or he works in the CLI. Each block below does one job. Most live in .github/, so the whole team shares them through git.

BlockQuestion it answersRepo fileWhen it applies
Custom instructionsWhat should Copilot always know here?.github/copilot-instructions.md, AGENTS.mdEvery chat/agent request
SkillsHow do we do task X, step by step?.github/skills/<name>/SKILL.mdWhen you type /name, or the model decides it fits
Custom agentsWho is doing the work, with which tools?.github/agents/<name>.agent.mdWhen you pick that agent
ToolsWhat can the agent actually do?Built in, plus MCPEvery tool call, subject to approval
HooksWhat must always happen, no matter what the model thinks?.github/hooks/*.jsonLifecycle events (before/after tools, session start…)
MCP serversWhich outside systems can it reach?.mcp.json (or .vscode/mcp.json)Their tools join the tool list
Instructions (always)→Agent (persona + tool limits)→Skill (task recipe)→Tools + MCP⇄Hooks (guardrails)
💡

Rule of thumb: if the model may skip it, it is guidance (instructions, skills, agents). If it must never be skipped, it is a hook or a permission. Plugins bundle skills, agents, hooks and MCP servers into one installable package (/plugin in the CLI).

⚠️

VS Code's Local harness is deprecated (removal planned by February 2027). Prompt files, agent handoffs and the .vscode/mcp.json servers format belong to it. This page uses the default Copilot harness, which shares formats with the CLI.

Custom instructions: the base layer

Everything else builds on these. The full story, including AGENTS.md and Copilot Memory, is in 8 · Knowledge & learning loop. Here is the short version for ShipTrack.

northwind/shiptrack
.github/
├── copilot-instructions.md          repo-wide, always loaded
└── instructions/
    └── tests.instructions.md        only when files match applyTo
AGENTS.md                            cross-tool instructions (nested files supported)
.github/instructions/tests.instructions.mdnew
--- name: ShipTrack tests description: How we write pytest tests for the API applyTo: "tests/**" --- # Testing rules - Use pytest with httpx.AsyncClient against the FastAPI app; no live network. - One test module per router: tests/test_<router>.py. - Cover the happy path plus 404 and 422 for every endpoint. - Use the db_session fixture from tests/conftest.py; never touch a real database.
  • Instructions shape chat and agents. They do not affect inline suggestions.

  • Generate a starter file with /init in the CLI; list what is loaded with copilot instruction list.
🛠️ Skills

Skills: reusable task recipes

A skill is a folder with a SKILL.md that teaches one task. Skills follow the open agentskills.io standard, so the same folder works in VS Code, the CLI and other compatible tools. Priya writes one for "add an endpoint" because ShipTrack will get many.

Where skills live

ScopeFolders
Repo (shared).github/skills/<name>/, also .claude/skills/ and .agents/skills/
Personal~/.copilot/skills/, ~/.agents/skills/, ~/.claude/skills/
CLI extrasCOPILOT_SKILLS_DIRS environment variable; folders added with /add-dir
.github/skills/add-endpoint/SKILL.mdnew
--- name: add-endpoint description: Add or change a ShipTrack REST endpoint: Pydantic v2 schema, SQLAlchemy 2 query, router, Alembic migration if needed, and pytest tests. Use whenever a task adds or modifies an HTTP route. argument-hint: "METHOD /path, e.g. POST /shipments/{id}/events" --- # Add a ShipTrack endpoint ## Steps 1. Read app/routers/ and app/schemas/ to match existing style. 2. Add request/response models in app/schemas/ (Pydantic v2, model_config = ConfigDict(from_attributes=True)). 3. Add the query in app/repositories/ using SQLAlchemy 2 select() style; no raw SQL. 4. If the table changes, create a migration: alembic revision --autogenerate -m "<summary>". 5. Add the route in the matching router; return 404 with {"detail": "..."} when not found. 6. Write tests in tests/test_<router>.py: happy path, 404, 422. 7. Run: ruff check . && ruff format --check . && pytest -q ## Done when - All commands in step 7 pass. - The endpoint appears in /docs with an example.

Frontmatter rules

  • name (required): in VS Code use lowercase letters, numbers and hyphens, at most 64 characters, and match the folder name. The CLI is looser, but follow the strict rule so both work.
  • description (required, up to 1,024 characters): the model reads this to decide when to use the skill, so say when, not only what.
  • Optional: argument-hint, user-invocable, disable-model-invocation; the CLI also reads allowed-tools.

Use it

bash — shiptrack
› /skills list add-endpoint Add or change a ShipTrack REST endpoint ... (project) › /add-endpoint GET /shipments/{id}/events ● Using skill: add-endpoint ● Read app/routers/shipments.py, app/schemas/shipment.py ● Edit app/schemas/event.py, app/repositories/events.py, app/routers/shipments.py ● Create tests/test_shipment_events.py ? Run: ruff check . && ruff format --check . && pytest -q [allow once / session / repo] ✓ 9 passed in 1.4s

In VS Code the same skill appears as /add-endpoint in chat. Edit a skill and run /skills reload in the CLI to pick up changes.

ℹ️

Skills replace prompt files (.github/prompts/*.prompt.md), which only work in VS Code's deprecated Local harness. A shared marketplace for customizations exists preview; check current docs before relying on it.

🤖 Agents

Custom agents: a persona with limited tools

Marco reviews every ShipTrack PR. He wants a reviewer agent that reads code and checks it against the team's rules but can never edit a file.

.github/agents/reviewer.agent.mdnew
--- name: reviewer description: Reviews ShipTrack changes against team standards. Read-only: reports findings, never edits. tools: ['read', 'search'] user-invocable: true # CLI only: load repo instructions when this agent runs as a subagent include-custom-instructions: true --- You are a senior reviewer for the ShipTrack FastAPI service. ## Check every change for - Pydantic v2 schemas at the API boundary; no ORM objects returned directly. - SQLAlchemy 2 select() style; sessions from the dependency, never global. - Every new endpoint has tests for happy path, 404 and 422. - No secrets, tokens or connection strings in code or tests. ## Output A table: file, line, severity (blocker / should-fix / nit), finding, suggested fix. End with READY or NOT READY.

Frontmatter you will use most

KeyWhat it does
name, descriptionIdentity. description is required.
toolsAllowed tools. Aliases: execute read edit search agent web todo *, or <server>/* for an MCP server.
model, reasoning-effortPin a model (string or list) and effort.
skills, mcp-servers, hooksAttach skills, MCP servers and hooks to this agent only.
user-invocable, disable-model-invocationWho can start it: you, the model, or both.
targetvscode or github-copilot.
handoffs, argument-hintVS Code Local harness only (deprecated).

Run it

  1. Open the agent picker in the Chat view and choose reviewer (or create one with Chat: New Custom Agent).
  2. Ask: Review the changes on this branch.
bash — shiptrack
# start a session as the reviewer $ copilot --agent reviewer # or switch inside a running session › /agent
  • Other locations: .claude/agents/*.md, personal ~/.copilot/agents/ and ~/.claude/agents/. Old .chatmode.md files: rename to .agent.md.
  • In the CLI, an agent in a subfolder gets an ID with / replaced by -- (for example agents/api/reviewer.agent.md → api--reviewer).
  • The CLI also ships built-in subagents such as code-review, explore and security-review.
🔧 Tools

Tools: what the agent can do, and who says yes

Agents act through tools: read files, edit, run shell commands, fetch URLs, call MCP servers. You decide which tools exist in a session and which ones need your approval.

VS Code

Pick tools with the tool picker in chat, or limit them in an agent's tools: list. MCP tools appear alongside built-in ones.

Copilot CLI

Tool kinds: shell, read, write, url, and MCP tools as Server(tool). /env lists what is loaded.

Approval levels

SurfaceSafestMiddleRiskiest
VS Code (chat.permissions.default)Manual (default)Assisted: a safety model judges each callAllow all / Autopilot
CLI (/permissions)Default: reads auto-allowed, writes/shell/URLs prompt/permissions assisted/allow-all (/yolo)

When the CLI prompts, you can approve once, for the session, or remember for this repo (saved in ~/.copilot/permissions-config.json). In VS Code, Chat: Manage Tool Approval and Chat: Reset Tool Confirmations manage saved approvals.

Allow and deny lists in the CLI

Marco runs ShipTrack tasks with git, ruff and pytest pre-approved, and git push blocked outright:

bash — shiptrack
$ copilot --allow-tool='shell(git:*)' --allow-tool='shell(ruff:*)' --allow-tool='shell(pytest:*)' --deny-tool='shell(git push)' › Fix the failing test in tests/test_shipments.py and commit ● shell: pytest -q tests/test_shipments.py (allowed by --allow-tool) ● edit: app/routers/shipments.py (prompted: allow once) ● shell: git commit -am "Return 404 for unknown shipment" (allowed) ✗ shell: git push denied by --deny-tool # a read-only review session: no file writes at all $ copilot --agent reviewer --deny-tool=write
⛔

Deny always wins, even over --allow-all. But --allow-all//yolo without denies means a shell command can do anything your user account can: push, delete, call the network. Use it only in a sandbox or disposable worktree. See 5 · Security.

🪝 Hooks

Hooks: run your own code at fixed moments

Instructions ask; hooks enforce. A hook is a command (or HTTP call) that runs on a lifecycle event. The same JSON format works in the VS Code Copilot harness, the CLI, the Copilot app and the cloud agent.

Events you will use

EventFiresTypical use
sessionStart / sessionEndSession begins / endsPrint context, write an audit line
userPromptSubmittedYou send a promptLog or block prompts containing secrets
preToolUseBefore a tool runsAllow, deny or ask, with a reason
postToolUseAfter a tool succeedsFormat/lint; return additionalContext
agentStop, subagentStopAn agent finishesFinal checks
errorOccurred, preCompactErrors; before context compactionAlerts, saving notes

Also available: postToolUseFailure, subagentStart, userPromptTransformed, permissionRequest, notification. PascalCase names (for example PreToolUse) are Claude-style aliases with a different payload shape.

Example: keep ShipTrack ruff-clean after every edit

.github/hooks/ruff.jsonnew
{ "version": 1, "hooks": { "postToolUse": [ { "type": "command", "bash": "ruff check --fix --quiet . 1>&2; ruff format --quiet . 1>&2; echo '{}'", "powershell": "ruff check --fix --quiet . *> $null; ruff format --quiet . *> $null; '{}'", "cwd": ".", "timeoutSec": 30 } ] } }
  • I/O contract: the event payload arrives as JSON on stdin; the hook must print exactly one JSON object on stdout. That is why ruff's output goes to stderr and the command ends with {} ("no decision").
  • postToolUse fires after every tool call, including reads. Keep the command fast, or call a script that reads the payload and only acts on edits (field names are in the hooks reference).
  • A preToolUse hook answers with {"permissionDecision": "deny", "permissionDecisionReason": "…"} (or allow/ask). A reason is required on deny.

Failure rules (read twice)

SituationResult
Exit code 2Warning by default; deny for preToolUse and permissionRequest
preToolUse command crashes or exits non-zeroFail closed: tool blocked
Any hook times outFail open: normal permissions apply
HTTP preToolUse hook failsFail open
Any hook says denyTool blocked

Where hooks are loaded from

  • Repo: .github/hooks/*.json (the only source the cloud agent uses, Linux/bash). Personal: ~/.copilot/hooks/*.json.
  • Inline hooks key in .github/copilot/settings(.local).json, ~/.copilot/settings.json or .claude/settings*.json; plugin hooks.json; managed policy folders.
  • All sources run together. "disableAllHooks": true skips one file (policy hooks still run). In VS Code, /hooks opens the hooks UI. In the CLI, repo hooks need a trusted folder.
🔌 MCP

MCP: plug in tools from other systems

The Model Context Protocol lets a server expose tools (and sometimes resources) to the agent: GitHub issues, a database, a ticketing system. Servers run locally over stdio (command, args, env) or remotely over HTTP (http, alias streamable-http) or SSE.

⚠️

Two config formats exist. The CLI and VS Code's Copilot harness use a top-level "mcpServers" key. VS Code's deprecated Local harness uses "servers" in .vscode/mcp.json. Same idea, different key, and some fields don't carry over.

.mcp.json (repo root)committed
{ "mcpServers": { "github": { "type": "http", "url": "https://api.githubcopilot.com/mcp/" } } }
  • CLI files: project .mcp.json or .github/mcp.json; personal ~/.copilot/mcp-config.json. Project files load only in a trusted folder.
  • Priority, high to low: --additional-mcp-config, plugin servers, workspace files, user file.
  • VS Code Copilot harness reads the same Copilot user config ("Copilot Global") and a workspace-root .mcp.json experimental (chat.mcp.workspaceRootConfig.enabled offers it in MCP: Add Server).
  • The GitHub server URL is the remote endpoint documented in the github/github-mcp-server README; check it for current options and authentication. In the CLI, finish sign-in with /mcp auth if asked.
.vscode/mcp.jsonLocal harness · deprecated
{ "servers": { "github": { "type": "http", "url": "https://api.githubcopilot.com/mcp/" } } }
  • Also allowed here: "inputs" (prompted values), "sandbox", and per-server sandboxEnabled, envFile, dev. Do not copy inputs, envFile or dev into an mcpServers file.
  • Migrate to the shared format with one command:
bash — shiptrack
$ jq '{mcpServers: .servers}' .vscode/mcp.json > .mcp.json

The CLI ships the GitHub MCP server (github-mcp-server) enabled by default with a default toolset, so Marco needs no config to work with issues and PRs from the terminal.

bash — shiptrack
› /mcp list github-mcp-server built-in enabled › Summarise open issues labelled "api" in northwind/shiptrack ● github-mcp-server(list_issues) (prompted: allow for session) #12 GET /shipments/{id}/events returns 500 for unknown id #15 Add pagination to GET /shipments # more GitHub tools: --enable-all-github-mcp-tools or --add-github-mcp-toolset # turn built-ins off: --disable-builtin-mcps

Adding servers without editing JSON

  • VS Code: MCP: Add Server, MCP: Browse MCP Servers, or Chat: Open Customizations → MCP Servers.
  • CLI: /mcp add, /mcp edit, /mcp disable, /mcp reload, or the copilot mcp subcommand.
⛔

MCP servers can return text that tries to steer the agent (prompt injection), and stdio servers run code on your machine. Use servers your org has approved, keep tool approvals on, and never commit tokens into MCP files. Organisations can disable MCP or enforce an allowlist.

🧪 Lab

Lab: give ShipTrack a skill, a reviewer, a hook and MCP

About 40 minutes. Use a branch of northwind/shiptrack (or any small FastAPI repo). Your progress is saved in this browser.

  • 1. Instructions. Run /init in the CLI, then trim .github/copilot-instructions.md to ten lines of real ShipTrack rules. Add tests.instructions.md from Step 2.
  • 2. Skill. Create .github/skills/add-endpoint/SKILL.md from Step 3. Check it appears in /skills list and as /add-endpoint in VS Code chat.
  • 3. Agent. Create .github/agents/reviewer.agent.md from Step 4. Ask it to edit a file and confirm it can't.
  • 4. Hook. Add .github/hooks/ruff.json from Step 6. Ask the agent to add a badly formatted line; confirm ruff fixed it.
  • 5. Approvals. Start the CLI with the allow/deny flags from Step 5 and ask it to push. Confirm the deny.
  • 6. MCP. In the CLI run /mcp list; in VS Code add the GitHub server with MCP: Add Server. Ask both for open issues.
  • 7. Put it together. Run the flow below, then open a PR with all the new files for Marco to review.
