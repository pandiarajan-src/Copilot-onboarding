🌱 Scenario

A parcel-tracking API, from an empty repo

Northwind Logistics wants a small REST service that records shipments and their tracking events. The repo northwind/shiptrack exists and holds only a README.

docs/brief.mdowner: Marco · reviewed by Sam
# ShipTrack v1: parcel tracking API Problem: customer support answers "where is my parcel?" by phoning depots. We need one source of truth. v1 endpoints: POST /shipments create a shipment, returns a 12-char tracking number GET /shipments/{id} current status GET /shipments/{id}/events timeline, oldest first POST /shipments/{id}/events depot scans (picked_up, in_transit, out_for_delivery, delivered) Rules: events cannot be older than the latest event · nothing after "delivered" · unknown id = 404 Stack: Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2 + Alembic, PostgreSQL, pytest + httpx, ruff, GitHub Actions Out of scope: auth (handled by the API gateway), customer notifications, UI Done when: all endpoints tested, CI green on every PR, reviewed by Marco and Sam

📐 Foundations

Write the instructions before the first line of code

Copilot reads repository instructions on every chat and agent request. Five minutes here saves dozens of corrections later: stack, layout, commands and rules, written once.

.github/copilot-instructions.mdcommitted by Marco
# ShipTrack: instructions for Copilot ## Stack - Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2.0 typed ORM (`Mapped[...]`), Alembic, PostgreSQL 16. - Tests: pytest + httpx `AsyncClient` with `ASGITransport`. Lint and format: ruff. ## Layout - `app/api/` routers only, no SQL. `app/services/` business rules. - `app/models/` SQLAlchemy models. `app/schemas/` Pydantic models. - `migrations/` Alembic. Never edit an applied migration; add a new one. ## Commands - Install: `pip install -e ".[dev]"` - Test: `pytest -q` - Lint: `ruff check . && ruff format --check .` - Migrate: `alembic upgrade head` ## Rules - Write or update tests before changing behaviour. Never weaken a test to make it pass. - Missing resource: 404 with `{"detail": "..."}`. Validate input with Pydantic, not by hand. - Config from environment via pydantic-settings. No secrets in code or tests. - All timestamps are timezone-aware UTC. - Type-hint everything. Keep functions under ~30 lines. - Do not add a dependency without saying why in the chat.

Add a scoped rule for tests

Rules that only matter for some files go in .github/instructions/ with an applyTo glob, so they load only when relevant.

.github/instructions/tests.instructions.md
--- name: ShipTrack tests description: Conventions for pytest files applyTo: "tests/**/*.py" --- - One behaviour per test; name tests `test_<action>_<expected>`. - Use the `client` and `db_session` fixtures from `tests/conftest.py`. - No sleeps, no real network, no shared state between tests.

Create the file by hand, or open Chat: Open Customizations from the Command Palette to see which instruction files are active. Instruction files guide chat and agents; they do not change inline suggestions.

In an existing repo, /init (or copilot init) drafts a copilot-instructions.md for you. Here the repo is empty, so Marco writes it himself. copilot instruction list shows which sources the CLI loaded.

AGENTS.md is also read by Copilot and by other agent tools. Pick one primary file to avoid duplicated or conflicting rules. Northwind uses copilot-instructions.md for ShipTrack and AGENTS.md for Ledgerly (see Brownfield).

💡

Instructions are code: review them in a PR like any other file. More in Skills, Agents, Tools, Hooks, MCP.

🔧 Fix

Red, then green: fixing failures with the agent

The first run has two failures. Priya lets the agent read the output and fix the code, then checks the diff.

bash — shiptrack
$ pytest -q .........F..F. [100%] FAILED tests/test_events.py::test_add_event_older_than_latest_returns_422 TypeError: can't compare offset-naive and offset-aware datetimes FAILED tests/test_events.py::test_add_event_after_delivered_returns_409 assert 422 == 409 2 failed, 12 passed in 1.84s # Priya in chat: "Two tests fail, output above. Explain the root cause of each, # then fix the code. Do not change the tests." Copilot: 1) service compares a naive datetime from a helper with aware occurred_at. Fix: use datetime.now(UTC) in app/services/shipments.py. 2) ShipmentClosedError is checked after the ordering check, so 422 wins. Fix: check "delivered" first, map ShipmentClosedError to 409. $ pytest -q .............. [100%] 14 passed in 1.62s $ ruff check . && ruff format --check . All checks passed! 23 files already formatted $ git add -A && git commit -m "feat: shipments and tracking events API"

Good loop

Paste or point at the real failure, ask for the root cause first, then the fix. Re-run the full suite, not just the failing test.

Watch for

"Fixes" that loosen assertions, add try/except: pass, or mark tests skipped. Read the diff in the editor before you accept it.

When it loops

If the agent fails the same way three times, stop. Start a fresh chat with a narrower prompt, or fix it yourself and tell Copilot why.

📝 Retro

What the team keeps, and what it stops doing

From Priya and Marco's retro after ShipTrack v1 shipped.

Instructions before code

The UTC rule and "no SQL in routers" were followed from the first file because they were written down first.

Plan, then cut

Reviewing the plan removed a cache and settled two design questions before any code existed.

Small steps, commits between

One plan step per prompt, a commit after each. Every bad turn cost minutes, not hours.

Tests in a separate prompt

Tests written before the implementation caught two real bugs the agent would have papered over.

Anti-patterns

Anti-patternWhy it hurtsDo this instead
"Build the whole app" in one promptHuge diffs nobody reads; invented features; hard to undo.Plan first, then one plan step per prompt.
Accepting a migration unreadSchema mistakes are expensive and reach production.Read every migration; test downgrade().
Letting the agent edit tests to go greenThe suite stops protecting you."Do not modify tests" in the prompt; check the diff.
Allow all from day oneA shell tool can do anything your user can, including push.Manual approvals; deny risky commands like git push.
Rules repeated in every promptInconsistent, forgotten, long prompts.Put them in copilot-instructions.md once.
Trusting a confident answerModels can be wrong about libraries and versions.Ask "why?", run it, check official docs.
✓

After the retro Marco added one line to the instructions: "Generate IDs shown to customers with the secrets module." Each mistake Copilot makes twice belongs in the instructions file. More in Knowledge & learning loop.
