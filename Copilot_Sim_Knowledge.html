Step 1
🗺️ Context

The model doesn't know your codebase. Context does.

Every request is your prompt plus whatever context Copilot gathers. Good context is the difference between "a FastAPI endpoint" and "a ShipTrack endpoint".

Your prompt+Open files & references+Instructions & memory+Tool results→Model

Leo, the new joiner, asks Copilot for a new endpoint in ShipTrack. Without team context he gets working code that still breaks three team rules: synchronous DB calls, legacy SQLAlchemy queries and no error envelope. Marco rejects the PR. The fix is not a better prompt every time; it is writing the rules down once where Copilot reads them.

Custom instructions shape chat and agent responses. They do not affect inline suggestions as you type.

📄 Repo-wide

One file every request in the repo reads

.github/copilot-instructions.md holds the short list of things Copilot must know about this repo: stack, commands, conventions, no-go areas.

Marco bootstraps it with the CLI, then edits it down. /init (or copilot init) drafts the file from the repo.

bash — shiptrack
~/code/shiptrack$ copilot > /init …reads pyproject.toml, app/, tests/, .github/workflows/… Drafted .github/copilot-instructions.md (review before committing) > /instructions # see and toggle which instruction files are loaded > /exit ~/code/shiptrack$ copilot instruction list # list every instruction source
shiptrack/.github/copilot-instructions.mdsaved
# ShipTrack Parcel-tracking REST API for Northwind Logistics. ## Stack - Python 3.12, FastAPI, Pydantic v2 - PostgreSQL via SQLAlchemy 2 (async) + Alembic migrations - Tests: pytest + httpx AsyncClient. Lint: ruff. ## Commands - Install: `pip install -e ".[dev]"` - Test: `pytest -q` Lint: `ruff check . && ruff format --check .` ## Conventions - Routers live in `app/routers/`, one file per resource. - Request and response bodies are Pydantic models in `app/schemas.py`. - Errors use the envelope `{"error": {"code": ..., "message": ...}}`. - Read config from env vars via `app/config.py`. Never hard-code credentials. ## Don't - Don't edit files in `alembic/versions/` that are already merged. - Don't add dependencies without saying why.
  • ✓
    Keep it short and specific. Every line costs context on every request.
  • ✓
    Write facts and rules, not essays. Link to longer docs instead of pasting them.
  • ✓
    Review changes to it in pull requests like code. It changes how every agent behaves.
💡

Personal preferences go in ~/.copilot/copilot-instructions.md (or ~/.copilot/instructions/), not in the repo file. The CLI merges all locations it finds, from the git root and the current folder.

🎯 Scoped

Rules that apply only to matching files

Put rules for tests, migrations or one app in .github/instructions/. The applyTo globs decide when each file is used.

ShipTrack instruction layout
.github/
├── copilot-instructions.md          repo-wide
└── instructions/
    ├── tests.instructions.md        applyTo: tests/**/*.py
    └── migrations.instructions.md   applyTo: alembic/**
.github/instructions/tests.instructions.mdnew
--- name: ShipTrack tests description: How we write pytest tests for the API applyTo: "tests/**/*.py" --- - Use the `client` fixture (httpx AsyncClient) from `tests/conftest.py`. - Mark async tests with `@pytest.mark.anyio`. - One behaviour per test; name tests `test_<endpoint>_<behaviour>`. - Cover at least one error case (404, 422) for every endpoint.
.github/instructions/migrations.instructions.mdnew
--- name: Alembic migrations description: Rules for database migrations applyTo: "alembic/**" --- - Generate with `alembic revision --autogenerate -m "..."`, then review the script. - Every `upgrade()` has a working `downgrade()`. - Never edit a migration that has been merged; add a new one.
FrontmatterMeaning
applyToComma-separated globs relative to the repo root. ** means every file.
name, descriptionLabel the file so people (and Copilot) know what it covers.
ℹ️

Same idea at user level: ~/.copilot/instructions/**/*.instructions.md. Claude-style rule files in .claude/rules/ are also read (with paths or applyTo frontmatter).

🤝 Cross-tool

AGENTS.md: one file many AI tools read

If your team uses more than one coding agent, put shared guidance in AGENTS.md. Copilot reads it alongside its own instruction files.

In Ledgerly, Marco uses a root AGENTS.md for the whole monolith and a nested one for the risky invoices app. Nested files are supported, so guidance sits next to the code it describes.

Ledgerly
ledgerly/
├── AGENTS.md                 whole repo: Django 3.2 → upgrade, Celery, test commands
├── invoices/
│   ├── AGENTS.md             views.py is being refactored; add characterization tests first
│   └── views.py              600 lines
└── billing/ customers/ payments/ reports/
ledgerly/AGENTS.mdsaved
# Ledgerly Django 3.2 invoicing monolith, upgrading. Apps: billing, customers, invoices, payments, reports. ## Before changing code - Run `python manage.py test <app>` for the app you touch. Coverage is thin (~30%). - Add a characterization test that pins current behaviour before refactoring. ## Shared docs @docs/architecture.md

That last line is an import: the Copilot CLI supports @path imports in AGENTS.md, CLAUDE.md and copilot-instructions.md, so you can keep long docs in one place.

UseWhen
.github/copilot-instructions.mdCopilot-only repo guidance.
AGENTS.mdGuidance shared with other agents, or folder-level guidance next to the code.
CLAUDE.mdAlready have one? Copilot reads it too; no need to duplicate.
⚠️

In VS Code's deprecated Local harness, nested AGENTS.md files sit behind an experimental setting (chat.useNestedAgentsMdFiles, off by default). In the CLI, custom agents (subagents) do not get repo instructions unless their file sets include-custom-instructions.

🔁 Reuse

Reusable prompts: prompt files are legacy, skills are the path

Instructions say how to work. A reusable prompt captures a task you run often, like "add an endpoint with tests".

⚠️

Prompt files work only in VS Code's Local harness, which is deprecated and due for removal by February 2027. The default Copilot harness and the CLI use skills for reusable tasks. Migrate prompt files to skills.

.github/skills/add-endpoint/SKILL.mdnew
--- name: add-endpoint description: Add a ShipTrack REST endpoint with schema, router, tests and docs. Use when asked to add or extend an API route. --- 1. Add or reuse Pydantic models in `app/schemas.py`. 2. Add the route in `app/routers/<resource>.py`, using the async session dependency. 3. Write tests in `tests/test_<resource>.py`: happy path, 404 and 422. 4. Run `ruff check .` and `pytest -q`; fix until both pass.

Run it as /add-endpoint in VS Code chat or the CLI, or let the model pick it up from the description. In the CLI, /skills lists what is loaded.

.github/prompts/add-endpoint.prompt.mdlegacy
--- name: add-endpoint description: Add a ShipTrack endpoint with tests argument-hint: METHOD /path --- Add the endpoint the user describes, following our instructions, with tests.

Invoked as /add-endpoint in Local-harness chat; /prompts lists them and Chat: New Prompt File creates one. Prompt-file support in the CLI is not documented; use skills there.

💾 Memory

Copilot Memory: what Copilot learns by itself

Instead of only reading files you wrote, Copilot can store facts it discovers while working and reuse them later.

⚠️

Check current docs. Copilot Memory is evolving quickly: availability, policy names and limits below reflect the docs at the time of writing and may change.

Repository facts

Conventions, architecture, build and test commands. Scoped to one repo, shared with its collaborators, and cited back to the code.

User preferences

Your personal style. Follow you across repos; cited with quotes from your sessions.

WhoControl
PlansAvailable on paid plans. On Business and Enterprise it is off until an org or enterprise owner enables the policy.
OwnersAllow repo facts for all, selected or no repos; set an expiry for repo facts between 7 and 180 days; export or delete members' user preferences.
Repo adminsTurn Memory off for a single repo.
YouReview and delete your memories on the Memory page in your personal settings.

Memory in the CLI

bash — shiptrack
# Preview an import of team facts (JSONL) without writing anything $ copilot memories import shiptrack-facts.jsonl --dry-run $ copilot memories import shiptrack-facts.jsonl --on-conflict skip # Memory is not used in -p runs unless you opt in $ copilot -p "Summarise how tests are run here" --enable-memory
💡

Memory complements instructions; it doesn't replace them. Rules the team agrees on belong in reviewed files. Memory is good at the long tail of facts nobody wrote down.

🗂️ Spaces

Copilot Spaces: curated context on github.com

A Space gathers the files, docs and notes for one topic so people can ask Copilot questions grounded in them.

⚠️

Check current docs. The exact current behaviour of Spaces (what you can add, sharing rules, limits) was not verified for this guide. Treat the ideas below as patterns, not a feature list.

Good fit

Cross-repo knowledge: Northwind's API style guide, the parcel-status state machine, the incident runbook. Things that don't belong to one repo.

Not a fit

Rules every agent must follow inside a repo. Those go in instruction files, versioned with the code.

From your editor

The GitHub MCP server exposes Spaces tools in some clients, so an agent can pull a Space's content into a session.

Leo's onboarding Space at Northwind holds the ShipTrack brief, the API style guide and links to both repos' instruction files. He asks it "what's our error format?" before writing code.

🔄 Loop

Turn every correction into team knowledge

When you correct Copilot twice for the same thing, the correction belongs in a file, not in your head.

1 Correct→2 Capture→3 Verify→4 Share↺
StageWhat you doOutput
CorrectSpot the wrong pattern in a diff and fix it in the session.A working change.
CaptureWrite the rule as one imperative line in the narrowest file that fits.Edited instruction or skill file.
VerifyStart a fresh session and repeat the original request. Check the rule is applied.Evidence the rule works.
ShareOpen a PR; the owner reviews and merges. Everyone's next session gets it.Team-wide behaviour change.

Worked example: Priya and the legacy query style

🤖 VS Code · Copilot Chat Agent · shiptrack
Priya
Add GET /shipments/{id}/events returning events newest first.
Copilot
Added the route in app/routers/shipments.py:
events = db.query(Event).filter(Event.shipment_id == id)...
Priya
Correct: We use SQLAlchemy 2 style with the async session: await session.scalars(select(Event).where(...).order_by(Event.created_at.desc())). No session.query(). Please fix.
Copilot
Updated to select() with AsyncSession; tests pass.
Priya
Capture: Add that rule to a new instructions file for app/**/*.py, one line, and show me the diff.
Tool
Created .github/instructions/database.instructions.md (Priya reviews and approves the write).
.github/instructions/database.instructions.mdnew
--- name: Database access description: SQLAlchemy 2 async patterns for ShipTrack applyTo: "app/**/*.py" --- - Query with `select()` on an `AsyncSession` (`await session.scalars(...)`). Never use `session.query()`. - Get the session from the `get_session` dependency; never create engines in routers.

Verify: Priya opens a new chat and asks for GET /shipments/{id}. The response uses select() without being told. Share: she opens a PR; Marco, who owns .github/instructions/, approves it. Leo's next endpoint is right the first time.

💡

In the CLI, /chronicle mines your session history (for example for tips or improvements), and /feedback sends feedback to GitHub. Use them to find corrections worth capturing.

👥 Team

Run knowledge like code

Instruction files are shared configuration for every developer's agent. Give them owners, reviews and a cleanup rhythm.

  • ✓
    Owners: Marco owns .github/copilot-instructions.md, .github/instructions/ and AGENTS.md via CODEOWNERS. Sam co-owns anything about secrets or auth.
  • ✓
    One rule, one place: repo-wide facts in the repo file, scoped rules in .instructions.md, tasks in skills. No copies.
  • ✓
    Small PRs: each captured correction is its own PR, linked to the session or PR where it came up.
  • ✓
    Verify on review: the reviewer reruns the triggering prompt in a fresh session before approving.
  • ✓
    Monthly prune: delete rules that tools (ruff, CI) now enforce, and merge duplicates. Shorter files work better.
  • ✓
    Onboarding: new joiners like Leo read the instruction files on day one; they are the team's living style guide.
SignalAction
Same review comment on two agent PRsCapture as an instruction.
A rule the linter can checkMove it to ruff config; drop it from instructions.
Multi-step task repeated weeklyTurn it into a skill.
Knowledge spanning several reposCurate it in a Space or a shared doc imported with @path.
