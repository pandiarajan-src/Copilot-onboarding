Modules

L100

M1 · Foundations

45 min
  • Explain what Copilot does: inline and next edit suggestions, chat, agents, code review, the CLI and MCP tools.
  • Describe the loop: your prompt plus gathered context goes to a model; agents call tools, read results and continue.
  • Know how usage is billed in GitHub AI Credits and why premium models cost more credits.
  • State the ground rules: review every change, never paste secrets, keep tool approvals on.
Guide: Introduction and Feature Tour.
L100

M2 · Setup

45 min
  • Sign in to Copilot in VS Code from the status bar on Windows, macOS or Linux.
  • Install the Copilot CLI with npm, WinGet, Homebrew or the install script, and log in with /login.
  • Find the user config folder ~/.copilot and the repo-level .github/copilot/settings.json.
  • Check the installed version with copilot version and update with copilot update.
Guide: Setup simulator. Lab: Lab 1.

M3 · Chat & Agent mode

90 min
  • Pick the right built-in agent: Ask for read-only questions, Plan (/plan) to agree an approach, Agent to make changes.
  • Choose a model in the model picker, or leave it on auto.
  • Use the permission levels Manual, Assisted and Allow all, and know that Autopilot auto-approves.
  • Run parallel sessions in the Agents window with Branch or New Worktree isolation.
Guide: Feature Tour and Greenfield run. Lab: Lab 3.

M4 · Copilot CLI

90 min

  • Isolate work with /new worktree or git worktree add, and hand off with /delegate.
  • Script non-interactive runs with copilot -p and scoped --allow-tool / --deny-tool flags.

M5 · Customization: instructions, skills, agents, hooks, MCP

M6 · Security

75 min

  • Treat MCP output, web pages and repo files as possible prompt injection. Content exclusion is not a security boundary.

Hands-on labs

Each lab is a real task on a real machine. Use a scratch copy of the repos, not production. Every lab ends with a checklist you can tick.

Lab 1 · Set up and send your first prompts 30 min

Leo's first morning. Goal: Copilot working in VS Code and in the terminal, and three useful answers about ShipTrack.

  1. Install the latest stable VS Code from code.visualstudio.com.
  2. Click the Copilot icon in the status bar, choose Use AI Features and sign in with GitHub. (Command Palette alternative: GitHub Copilot: Sign in.)
  3. Install the CLI with one command for your OS (table below). Windows needs PowerShell 6 or later; npm needs Node.js 22+.
  4. Run copilot version to confirm the install.
  5. Clone ShipTrack, start copilot in it, trust the folder when asked, and run /login.
  6. In VS Code Chat, pick Ask and send: "Explain the folder layout of this repo and where the API routes live."
  7. In the CLI send: "Which commands run the tests and the linter here? Read the config files, don't guess."
  8. Run /usage to see what your session used in AI Credits.

Lab 2 · Write copilot-instructions.md for ShipTrack 40 min

Priya and Marco agree the house rules once, so every chat and CLI session follows them.

  1. In the CLI, run /init to draft .github/copilot-instructions.md from the repo.
  2. Edit the draft down to short, checkable rules: stack, layout, commands, testing rule, never-do list. Aim for under 40 lines.
  3. Add a scoped file .github/instructions/tests.instructions.md with applyTo: "tests/**" for test-only rules.
  4. Confirm the files load: copilot instruction list in a terminal, or /instructions inside a session.
  5. Ask the same question with and without the file (toggle it in /instructions): "Add a GET /shipments endpoint." Compare the answers.
  6. Open a pull request so Marco can review the rules like any other code.
.github/copilot-instructions.mddraft
# ShipTrack: instructions for Copilot ## Stack - Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2, Alembic, PostgreSQL. - Pydantic schemas live in app/schemas/, ORM models in app/models/, routers in app/api/. ## Commands - Tests: pytest -q - Lint and format: ruff check . and ruff format . ## Rules - Every new endpoint ships with tests: one happy path, at least two error cases. - Schema changes go through a new Alembic revision. Never edit an applied revision. - Return Pydantic models from routes, not ORM objects. ## Never - Commit secrets or .env files. - Add a dependency without saying why in the PR.
.github/instructions/tests.instructions.mdnew
--- name: tests description: Rules for ShipTrack tests applyTo: "tests/**" --- - Use httpx with the FastAPI app; no live network calls. - One behaviour per test; name tests test_<endpoint>_<case>.

Lab 3 · Build an endpoint with tests in agent mode 60 min

Priya adds GET /shipments/{id}/events in VS Code. Plan first, then let the agent work with Manual approvals.

  1. Create a branch: git switch -c feat/shipment-events.
  2. In Chat, run /plan with the prompt below. Read the plan. Push back on anything that breaks your instructions file.
  3. Switch to Agent. Keep the permission level on Manual so you approve each command and edit.
  4. Ask the agent to write the tests first and run them, so you see them fail.
  5. Let it implement the route, then run pytest -q and ruff check . until both pass.
  6. Read the full diff yourself. Check the 404 path, ordering of events and the response model.
  7. Commit and open a pull request.

Lab 4 · Use the CLI in a worktree 45 min

Marco tightens the ruff rules without disturbing Priya's branch. A worktree gives the agent its own copy of the files.

  1. From the ShipTrack folder, create a worktree: git worktree add ../shiptrack-ruff -b chore/ruff-rules. (Inside a session, /new worktree does the same job.)
  2. cd ../shiptrack-ruff and start copilot. Trust the new folder.
  3. Press Shift+Tab until the mode shows plan, then send the prompt below.
  4. Approve the plan, switch back to standard mode and let it work. Approve commands once, not for the whole session.
  5. Check the result with !git diff --stat and !ruff check ..
  6. Run /review for a Copilot review of the change before you commit.
  7. Commit, push, and open the PR with /pr create. When merged, remove the tree: git worktree remove ../shiptrack-ruff.
bash — shiptrack-ruff
$ git worktree add ../shiptrack-ruff -b chore/ruff-rules $ cd ../shiptrack-ruff && copilot # Shift+Tab → plan mode > Enable ruff rule sets for imports and bugbear in pyproject.toml, fix what they flag, no behaviour changes. > !git diff --stat > /review > /pr create
⚠️

A worktree isolates files only. The agent can still reach your network and anything your user account can. Keep approvals on.

  • Started copilot in the worktree and trusted it
  • Used plan mode (Shift+Tab) before any edits

Lab 5 · Add an MCP server 45 min

MCP servers give the agent new tools. Start with the built-in GitHub server, then add one server from Northwind's approved list and have Sam review it.

  1. In the CLI run /mcp list. The built-in GitHub MCP server is on by default.
  2. Try it: "List open issues labelled bug in northwind/shiptrack." Approve the tool call once.
  3. Pick one server from the approved list. In VS Code use MCP: Browse MCP Servers or MCP: Add Server; in the CLI use /mcp add.
  4. To share it with the team, put it in .mcp.json at the repo root under the mcpServers key (shape below). The CLI only loads it in a trusted folder.
  5. Run /mcp show and check which tools the server exposes. Disable any you don't need.
  6. Ask Sam to review the config: who publishes the server, what it can reach, where credentials come from.
.mcp.jsonnew
{ "mcpServers": { "approved-server": { "command": "<command from the server's README>", "args": ["<arguments>"] } } }
⚠️

Never put tokens in .mcp.json. Treat everything an MCP server returns as untrusted input that could carry prompt injection. The .vscode/mcp.json file with a servers key belongs to the deprecated Local harness.

  • Listed servers with /mcp list
  • Used a GitHub MCP tool and approved it once
  • Added one approved server
  • Committed a shared .mcp.json with no secrets
  • Checked its tools with /mcp show
  • Sam reviewed and signed off the config

Lab 6 · Brownfield characterization tests on Ledgerly 90 min

Before anyone refactors the 600-line invoices/views.py, Leo and Priya pin down what it does today, including its odd behaviour.

  1. Create a branch: git switch -c test/invoice-views-characterization.
  2. In Ask, map the file: "List every view in invoices/views.py with its URL, HTTP methods, permissions and side effects (emails, Celery tasks). Don't change anything."
  3. Pick three views with the most business logic. Ask for characterization tests that record current output, quirks included. Tell the agent not to fix bugs it finds; list them instead.
  4. Run python manage.py test invoices. Every new test must pass against the unchanged code.
  5. Mutate one line by hand (for example a rounding call) and confirm at least one test fails. Revert.
  6. Record what you learned in AGENTS.md: test command, settings module, Celery in tests, known quirks.
  7. Open the PR. The refactor waits for a separate PR once these tests are merged.
